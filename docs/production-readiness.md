# 生产化闭环文档（阶段 5 · 块 C）

把「能跑起来的 MVP」升级为「客户生产环境可长期稳定运行的闭环」。本文覆盖生产就绪、可观测、备份容灾、SLA 值守、升级补丁、客户支持、安全运营常态化七个环节，与 `RUNBOOK.md`（启停排障）、`src/deploy/K8S_DEPLOY.md`（K8s 编排）、`SECURITY.md`（安全基线）、阶段 3 合规（等保三级 / 密评）衔接。

## 1. 生产就绪清单（Go-Live Checklist）

上线前逐项勾选，任一红项不得上线。

### 1.1 基础设施
- [ ] PostgreSQL 16+ 高可用（主从 / 托管），`DATABASE_URL` 统一经 `normalize_database_url()`

### 1.3 数据层

- [ ] 多租户 `tenant_id` 列就位，列表端点按租户隔离（阶段 3）

### 1.4 可观测与容灾

## 2. 可观测性

| 维度 | 方案 | 关键指标 |
|---|---|---|
| 指标 Metrics | Prometheus + Grafana | QPS、P99 延迟、错误率、GPU 利用率、队列深度 |
| 日志 Logs | 结构化日志 → Loki/ELK | 请求链路 ID、审计事件、异常堆栈 |
| 链路 Traces | Langfuse（LLM 可观测） | token 消耗、tool_calls 成功率、ReAct 步数 |
| 告警 Alerts | Alertmanager | 错误率 >1%、延迟 P99 >2s、PG 连接耗尽、Qdrant 不可用 |

**建议 SLO（内部基线，非对外承诺）**：
- API 可用性 ≥ 99.5%（月度）
- P99 延迟 ≤ 2s（非推理类请求）
- 推理请求失败率 ≤ 2%（不含模型本身限流）

## 3. 备份与容灾

| 组件 | 备份方式 | 频率 | RPO | RTO |
|---|---|---|---|---|
| PostgreSQL | `pg_dump` / 物理备份（WAL 归档） | 每日全量 + WAL 增量 | ≤ 5 min | ≤ 30 min |
| Qdrant | 快照（snapshot API） | 每日 | ≤ 24h | ≤ 1h |
| Redis | RDB/AOF 持久化 + 主从 | 持续 | ≤ 1 min | ≤ 10 min |
| 对象存储 | 跨区复制 / 版本化 | 实时 | 近 0 | ≤ 30 min |

**恢复演练（强制）**：每季度至少一次从备份恢复 PG + Qdrant 到隔离环境，验证数据一致性与脚本可用性；记录演练报告。

**多租户隔离**：备份按租户可单独恢复；恢复前确认 `tenant_id` 过滤未失效，避免跨租户串扰。

## 4. SLA 与值守

| 等级 | 客户类型 | 可用性目标 | 响应 | 解决 |
|---|---|---|---|---|
| 旗舰版 | 央企/金融 | 99.9% | 15 min | 4h（P1） |
| 行业定制版 | 头部民企 | 99.5% | 30 min | 8h（P1） |
| SaaS 版 | 中型 | 99.0% | 1h | 下一个工作日 |

**事件分级**：
- P1 生产全阻 / 数据丢失风险 → 立即电话 + 拉群 + 值班 On-call
- P2 核心功能降级 → 2h 内响应
- P3 非核心 / 咨询 → 工单排队

**On-call**：7×24 轮值（旗舰版）/ 工作制（其余）；升级路径 P1→架构师→研发负责人。

## 5. 升级与补丁流程

基于 `K8S_DEPLOY.md` 的 Helm 编排（HPA 弹性 + Nginx Ingress 权重灰度）：

1. **镜像构建**：CI 出带 tag 镜像（语义化版本，禁止 `latest` 上生产）。
2. **数据库迁移先行**：`alembic upgrade head` 在灰度前单独执行，失败即停（兼容「优先 alembic，失败回退 create_all」）。
3. **灰度发布**：Ingress 权重 10% → 50% → 100%，每档观察 SLO 与告警。
4. **回滚**：Helm `rollback` 到上一 revision；若涉及破坏性迁移，按 `down_revision` 反向 `alembic downgrade`（0004 已具备 downgrade）。
5. **补丁（安全/CVE）**：走同一灰度通道，紧急 P1 可跳过 50% 档但需双人确认。

> 迁移安全铁律：所有新增表/列必须带 `down_revision`，禁止在生产执行无回滚路径的 DDL。

## 6. 客户支持模型

| 层级 | 职责 | 渠道 |
|---|---|---|
| L1 一线支持 | 工单受理、常见问答、收集信息 | 工单系统 / 客户群 |

- 知识库：将高频问题沉淀回 `docs/` 与社区 `examples/`，反哺售前与交付。
- 客户成功：每季度业务复盘，推动 Killer Scenario 扩展（对应规划 2026.12 行业场景沉淀）。

## 7. 安全运营常态化

阶段 3 已落地的合规能力转入日常运营，而非一次性交付：

| 能力 | 状态 | 日常运营动作 |
|---|---|---|
| 等保三级 | 方案已落地（规划 2027.03 测评） | 季度自检：密码策略 / 限流 / 审计完整性哈希 |
| 密评 SM2/3/4 | 已实现（单测 8/8 全绿） | 密钥轮换策略；SM3 哈希校验定时跑 |
| 内容审核 | 双通道（block/redact） | 词表与规则库随合规要求更新 |
| 审计 | 调用级埋点 + SM4 落盘 | 审计日志定期复核，异常访问告警 |
| 多租户隔离 | ORM + API 双重隔离 | 新增端点默认带 `tenant_id` 过滤，代码评审卡点 |

> 安全运营原则：**合规不是上线门槛，而是持续状态**。任何新端点/新资源类型必须默认继承租户隔离与审计埋点。

## 8. 生产化闭环校验

判定闭环已闭合的最低证据（建议写入交付验收）：
- [ ] Go-Live Checklist（§1）全绿
- [ ] 可观测三件套（指标/日志/链路）有数据、有告警
- [ ] 备份恢复演练报告存在且通过
- [ ] SLA 值守与工单通道可用
- [ ] 一次真实灰度升级 + 回滚演练成功
- [ ] 安全运营自查季度机制就位

> 闭环标志：客户生产环境**不依赖原厂驻场**即可稳定运行、可观测、可恢复、可升级、可支持。
